# RDC 资源引用解耦：升级、备份与回退操作说明

适用范围：`082_resource_configuration_history.sql`、`083_run_resource_snapshots.sql`、`084_vector_compatibility.sql` 及配套 API/后台/Web。本文是操作方案和作者验证记录，不是生产发布记录或部署授权。生产数据库、主密钥、用户运行和真实服务均未在本专项中操作。

## 发布入口与前提

继续使用 `scripts/deploy-platform.ps1`，不新增第二套部署或生产恢复脚本。本次同时修改前后端和数据库，应走完整部署，不能只发布后端。生产页面访问的既有拒绝仍然有效；未完成独立审查、QA 和允许的界面验收前不执行发布。维护窗口与实际生产变更仍由主任务按授权安排。

发布前记录待发布提交、分支 `onwer_agent`、迁移前 schema_migrations 清单、服务版本、备份目录及文件摘要。不要把当前工作区未提交文件当作可回退版本，也不要在日志、工单或文档中保存连接串、密钥或备份正文。

复用原发布流程：准入栅栏阻止 HTTP 写入和后台领取；受管停止 API/Ask/Work/Ops；确认心跳、活动运行和外部执行状态；创建离线备份并验证 manifest；执行 `app.manage migrate`；准备管理员并启动已审查的新版本；构建 Web；运行既有健康检查。预检只证明预检项目，不证明升级或业务验收已经成功。

有 RUNNING、STARTED、SENDING 或结果未知的外部写操作时，不能为了备份强行把状态改成完成。先按现有核对流程停止并保留证据；原备份程序会拒绝仍有活动后台或执行中任务的情形。不要绕过该检查。

## 082～084 的数据语义

- 082 增加配置修改证据。旧资源只建立 `BASELINE / system:migration082 / baseline=true` 的上线基线，changes 为空；这不是还原过去的修改。模型、Agent/Workflow 发布定义和密钥不批量重写。
- 083 新增执行阶段及资源快照、实际调用关联和安全恢复标记。旧运行不会用当前配置补造快照或“已使用”证据。
- 084 新增向量身份/维度及兼容核对证据。旧文档、记忆、图片和视频的 vector_fingerprint 保持 NULL；有旧 dimensions 也不能推断模型身份兼容。按产品提供的核对/关键词降级/重建路径处理，不把未知批量填成当前身份。
- 普通 PENDING 且没有旧审批、操作执行凭据、模型调用或检查点等执行证据的任务保持原状，在真正开始时解析当前资源。已发布的模型修订和 resource_pins 仍保留为历史依据，不能批量改成当前值冒充过去。

## 旧审批与旧沙箱的隔离

升级前缺少运行资源快照，不能证明旧命令引用的 Skill 脚本、MCP 目标或接口就是恢复后挂载的内容。仅靠旧命令路径或审批 digest 不足以批准新内容。

083 在 SQL 事务内隔离以下无资源快照的 Work 运行：

1. WAITING_APPROVAL 或 PAUSED；
2. PENDING 且存在 work_approvals、operation_executions、本人的 Work 模型调用记录或持久检查点。

处理结果为 NEEDS_REVIEW，error_code=RESOURCE_HISTORY_MISSING，清除执行租约并更新 updated_at。Work 表没有 finished_at 列，本迁移不新增或伪造该字段。对应尚未 RELEASED 的沙箱设置 retention_required=true；已 RELEASED 的记录不改成可恢复。保留原审批决定、payload、操作凭据、成果及原检查点，不移动工作区资料、不取消运行、不自动重放。

保留的沙箱可能继续占用容量，需按现有救援流程核对并明确释放；不能为了放行新任务删除待核对资料。

同属这些 Work 运行且仍 RUNNING 的工作流改为 NEEDS_REVIEW 并记录 finished_at，包括 work_run_workflows 绑定和 external_workflow_jobs → api_credentials.parent_work_run 的工具/API 子调用。已完成或已取消的运行保持原状态。

界面通过原运行诊断说明“历史资源配置缺失，需人工核对”。不能在旧恢复按钮、审批提交、SQL 更新或后台脚本中把这批运行重新置为 PENDING。先用已有成果/救援流程核对资料、旧审批内容、目标和副作用；若需要重新执行，按明确授权建立新的运行或重新审批，并说明与原运行的关系。不能将这批历史缺失运行当成普通配置确认恢复。

## 备份与隔离恢复

仍使用 `app.backup create / verify / restore`。离线备份的完整 PostgreSQL dump 包含新表，data/model.key 必须与该数据库备份对应，附件、成果和现有源代码归档按原流程保留。备份目录沿用原私有访问控制；不得上传或展示主密钥。

配套完善原 backup.py：

- 清单计数覆盖 run_resource_stages、run_resource_snapshots、embedding_compatibility_evidence。对升级前尚不存在的表按旧版本缺表处理，不生成假的旧快照。
- 隔离恢复先验证 pg_restore 原始记录数与原 manifest，再执行新迁移。082 合法新增的 baseline 会增加 audit_events；不能在升级后用旧计数误报备份损坏。
- 迁移后继续验证凭据、附件与成果文件；新 execution_config 使用备份对应的 model.key 解密并验证 JSON。缺密钥、解密或内容校验失败必须停止，不吞掉错误或生成替代主密钥。

例如，在已核对备份目录后，从 `services/api` 执行原工具 `python -m app.backup verify --backup <已核对的目录>`，只做其受控隔离恢复验证。`restore` 也只创建原工具限定的独立恢复库/配置，不覆盖 owner_agent；它会关闭恢复副本的身份会话、凭据入口和后台执行条件。不能将该命令当作生产切换已完成。本文中的命令未在生产执行。

保留型恢复副本会隔离旧活动操作和浏览器/执行环境标识。真实运行中的容器、网页登录态和未知副作用不能因为数据库恢复而重新接管。保持 WORK_ENABLED 等开关关闭，核对副本证据后再制定明确的切换方案。

## 失败处理与回退条件

**SQL 迁移事务尚未提交时失败**：保留日志，保持后台停止。现有 migrate 在同一 SQL 连接事务中执行尚未应用的迁移，SQL 阶段异常会回滚该事务；专项测试强制失败证实 082～084 新结构、隔离状态及 schema_migrations 记录一起回滚，旧审批/检查点仍在。必须实际检查 schema_migrations 和表结构，不能只凭进程退出码猜测。检查点 setup 在 SQL 提交之后另行执行；它失败不代表前面的 SQL 迁移已经撤销。

**SQL 已提交，API/Web 构建、启动或验收失败**：保持准入关闭，停止已启动的新后台。原 Web 脚本恢复旧 .next 只是前端产物回退，不能视为数据库或整套代码已经回退。先备份当前失败现场及新阶段记录，再决定修复前进或经核对的完整恢复。

**出现任何升级后新数据时**：不允许简单切回旧码并删新表/新列。至少保全以下证据：

- run_resource_stages 中确认人、确认内容和阶段关系；run_resource_snapshots 中实际配置、凭据更新标记及使用时间；
- model_usage 的快照、阶段和实际参数关联；新增配置修改、兼容核对证据及通知原目标/消息/重试关系；
- RESOURCE_HISTORY_MISSING 隔离运行、保留沙箱、原审批/操作凭据、成果与检查点。

旧码不了解新执行阶段、向量兼容规则和目标确认边界，不能继续消费这些队列。即使旧码能连接升级后的 schema，也不等于可安全执行。不得把 NEEDS_REVIEW/PAUSED 改为普通排队来消除报错，不得把旧审批搬到新目标或脚本。

若确认回到升级前完整备份点，必须先核对所有备份点后的写操作与结果未知项，保留升级后证据并明确哪些新数据不能自动合并。只能在独立恢复库验证数据库、匹配主密钥、文件、代码与依赖组合；生产切换须满足本会话已授权范围和发布门禁，不得借回退隐式覆盖生产新数据。禁止就地 DROP 新表、反向重写 published 快照、覆盖生产库或用新钥匙尝试解密旧资料。没有通用、无损的逆向 SQL 迁移承诺。

## 升级后检查

- schema_migrations 包含 082、083、084 且没有错误；原用户、模型、Agent/Workflow 版本及当前发布指针仍在；密钥解密与文件摘要正常。
- 上线基线明确标记，原历史不足不填造；多资源调用可定位实际阶段/修订，未发起调用不标为已使用。
- 旧等待审批/暂停/审批后排队运行准确隔离，审批、操作凭据与检查点不变，非 RELEASED 沙箱保留，关联运行不在后台继续。
- 无审批、操作凭据、模型调用和持久检查点等执行证据的普通排队任务可在实际开始使用当前配置；停用、撤权、取消、租约和能力不兼容继续拦截。
- 旧通知缺少固定目标或原消息时停为 DELIVERY_HISTORY_MISSING，不自动投到更新后的通道；旧向量保持未知并提示核对/重建。
- 核对旧运行后再处理，不以错误计数归零作为成功标准。

## 作者验证与未验证事项

`tests/integration_tests/test_rdc_migration_upgrade.py` 仅接受显式 TEST_DATABASE_URL，来源库名必须以 _test 结尾，再自行创建随机 owner_agent_rdc_upgrade_<随机值>_test 库，测试结束仅删除自己创建的库。没有读取生产连接作为默认测试入口；运行者需为独立测试账号提供建库权限。

测试实际执行 001～081，建立加密模型/MCP、Agent/Workflow 版本、四类旧向量、旧通知、旧 MCP/Skill 审批、APPROVED 操作凭据、沙箱及真实 LangGraph 检查点，再执行 082～084。覆盖旧内容/主密钥不变、基线、未知兼容信息、隔离与保留、旧审批拒恢复、旧通知无外发、非零新表清单、SQL 失败回滚及旧备份计数与新基线的兼容流程。
