# 工作流版本历史、恢复与平台发布追溯需求

2026-11-03，知行平台产品需求 v1。需求编号 WVR。范围为工作流版本管理及本地软件发布追溯，不改智能对话 SSE，不扩大为多环境协作平台；保留已有数据和未提交改动。用户最新已允许提交并推送现有 origin，根协调者负责；本产品角色不操作 git。

## 1. GitHub 候选调研

候选范围为六个与可视化 Agent/自动化编排直接相关的开源项目，不是全 GitHub 全球排行。2026-11-03 11:41:56～57（GMT+8）从官方仓库页面内嵌 stargazerCount 读取精确数量；公开 API 首次因403限流，未伪称 API 成功。计数随时间变化，原始采集证据在 `.local/team-workspace/workflow-version/product/github-stars.json`。

- [n8n](https://github.com/n8n-io/n8n)：209,411。本次候选中最多；其[官方历史说明](https://docs.n8n.io/build/manage-workflows/view-change-history.md)区分版本与执行历史，支持只读预览、恢复、复制为新工作流，恢复前保存当前版本。完整历史有套餐限制，不能把所有开源部署等同商业功能。
- [Dify](https://github.com/langgenius/dify)：160,273。[官方版本控制](https://docs.dify.ai/en/cloud/use-dify/build/version-control)区分 Current Draft、Latest Version 和历史版本，支持预览与恢复草稿；恢复会替换草稿，发布是独立动作，部分能力受套餐限制。
- [Langflow](https://github.com/langflow-ai/langflow)：156,269。[官方 Build flows](https://docs.langflow.org/concepts-flows)明确保存快照、只读预览、恢复前备份当前草稿；预览不应触发自动保存覆盖。适合借鉴本平台的编辑保护。
- [Flowise](https://github.com/FlowiseAI/Flowise)：55,545。官方仓库页面显示已于2026-08-13归档；本轮仅作已有画布交互的历史参考，不推荐当持续维护依赖。查阅[官方 UI 源码目录](https://github.com/FlowiseAI/Flowise/tree/main/packages/ui/src/views)及现有文档，未足够确认与本需求完全相同的历史恢复/唯一当前发布版语义，不填成“全部支持”。
- [Activepieces](https://github.com/activepieces/activepieces)：25,348。[官方 Version History](https://www.activepieces.com/docs/flows/versioning)用草稿与已发布锁定版本分离，编辑发布内容产生草稿，用户可回到旧版继续编辑而不影响当前发布内容。
- [Coze Studio](https://github.com/coze-dev/coze-studio)：21,797。[官方工作流应用源码](https://github.com/coze-dev/coze-studio/blob/main/backend/application/workflow/workflow.go)有带版本/说明的发布与独立复制流程，[官方 API 参考](https://github.com/coze-dev/coze-studio/wiki/6.-API-Reference)有发布版调用语义。不能因存在代码复制入口就推断所有历史版本一键恢复路径与本方案相同。

本平台采用 n8n 的版本侧栏/复制入口、Dify 的草稿与生效版本分离、Langflow 的恢复前保护。以上为参考后的本地设计决策，不引入其运行时或承诺 DSL 兼容。静态交互示意见 [中文 Demo](demos/workflow-version-demo.html)，不连接网络或模型。

## 2. 当前项目已有能力与缺口

已核 `workflow_api.py`、`external_workflows.py`、`workflows.tsx` 和现有 schema：已有草稿 revision/CAS 保存、测试通过后发布、不可变 workflow_versions、已发布版本 active 上下架、明确版本执行、运行快照/来源修订。外部 API Key、Agent 与子流程已固定发布版，不可随 UI 切换重定向。

真实缺口：历史区只列运行与发布编号，未独立形成完整版本预览/恢复/复制；发布版未存历史画布 layout；active 表示可用，不能表示多个版本中的唯一“当前发布版”；本地未保存编辑在版本切换/恢复中需明确保护；开发版本不能仅用未提交仓库 HEAD 证明实际运行源码。

## 3. 状态契约（冻结）

1. **编辑草稿**：workflows.revision，只有此状态可编辑；未保存的浏览器修改不是已持久化版本。
2. **发布历史**：workflow_versions.version，不可变配置与资源 pins。active 控制能否执行，不等于当前。
3. **当前发布版**：workflows.current_published_version 可为空，最多指向本人该流程一个 active 版；独立 release_revision 为指针切换 CAS，不能用 draft revision 混代。

迁移旧流程时 current=NULL，不猜最高 active 是用户曾选的当前版；保留所有旧版 active 状态。新成功发布新版本自动设为当前，重复幂等发布既有版不悄悄切回它。下线当前版清空指针，不自动回退；重新启用旧版不自动设为当前。草稿保存/恢复不改变当前发布版。运行一旦准入固定原版及资源，不因指针切换改动执行内容。

## 4. 本轮需求与验收

### WVR-01 版本历史侧栏与当前状态

画布工具栏提供“版本历史”，与“运行记录”分开；显示当前草稿修订、当前发布版、各历史发布号、发布日期、来源修订及可用/已下线状态。当前版徽标唯一，空指针显示“尚未指定当前发布版”。侧栏可滚动，大量条目不挡住主操作；本期不删除单个发布版，避免损坏已有引用。

验收：旧版/当前版/下线版清晰可分，空历史中文空态；只读用户可以查看但无恢复/切换/复制写操作。切换侧栏和运行记录不把执行日志当配置版本。

### WVR-02 完整只读版本预览

点击发布历史进入预览，展示版本化 name、instructions、model_id、definition（含Schema/预算/节点参数）与 layout，不混用当前草稿参数。禁止画布编辑、保存、撤销或节点配置写入。顶部可返回原编辑草稿，返回后保留本地未保存内容。

新发布保存准确 layout。任何历史没有自定义 layout 时返回空对象/明确“此版本未保存自定义布局，按默认位置展示”，不得借当前草稿布局假称历史原画布；layout_known=false 只表示无自定义坐标，不能据此断言版本年代。不同版本快速切换，迟到详情不能盖掉新选择；失败显示失败，不把旧详情贴到新编号下。

验收：发布 v1 后更改模型/指令/节点/布局并发布 v2，分别预览准确；预览期间没有 PUT 草稿；dirty 编辑→预览→返回内容仍在。对历史无 layout、404/403、延迟与窄屏执行实际页面验证。

### WVR-03 恢复旧版为新草稿

恢复只复制选定历史的名称、模型、指令、图与布局到新草稿修订，使用当前草稿 revision CAS；恢复后 tested_revision/tested_pins 清空，须重新整体测试才能发布。历史版本、当前发布指针、旧运行及旧 Key 均不改。

有本地未保存改动时仅提供先保护再恢复或取消，不能隐式丢弃，也不写 localStorage 藏副本。**重要：仅PUT保存后又立即覆盖，不构成持久保留。恢复前编辑必须有可访问的备份（见恢复保护冻结补充）；保护失败不得执行 restore。** 本期不自动恢复旧模型密钥，也不以新模型偷换历史引用。已下线版本也可恢复成待修草稿；资源已停用/删除允许保留配置以便修复，运行/发布仍严格校验。

验收：新revision递增、测试资格清零；CAS409不覆盖服务端或本地内容；保护副本能从列表/历史找回；恢复不执行模型/工具；缺资源明确待修，不伪成功发布。

### WVR-04 复制旧版为独立工作流

历史预览提供“复制为新工作流”，可编辑名称，复制完整历史配置及可用布局，当前账号成为新流程 owner；新流程无 tested 状态、无发布版、无当前发布指针，不复制运行、Key、团队共享/审批实例或权限。原流程和其他版本保持。

当前浏览器草稿 dirty 时不强制跳新流程导致丢编辑：复制完成显示成功及“打开副本”入口，留在原编辑；用户明确打开副本前仍保护原本地编辑。源 inactive 可复制为待修草稿，源不存在/跨账号拒绝。

验收：副本可列表访问、独立编辑不改原图；没有伪造已测试/已发布标记；原脏草稿仍在；源模型/工具不可用不会被偷换，实际运行前再校验。

### WVR-05 切换当前发布版与明确运行路径

“设为当前发布版”调用独立 release_revision CAS，只接受 active 且实时配置/pins仍合法的本人版本，不改草稿。切换成功更新唯一徽标；冲突刷新最新发布状态，不能覆盖别人刚切换的结果。无效目标不自动上线或复制资源。

画布提供真正可用的“运行当前发布版”：读取明确 current 数字后，按原 `/versions/{n}/runs` 或原 Work 入口携明确 version 调用。选择 v1 为当前后，入口应预选 v1，不能显示 v1 徽标却继续默认跑 v2/草稿。测试草稿是独立操作。指针为空/当前已下线时给明确不可运行提示。

验收：v2→设v1当前→此入口实际发送v1；API Key、Agent、子流程原本固定v2的仍是v2。切换中原v2运行继续按固定快照，未知结果不自动重发；下线当前清空/重新启用不自动恢复指针；并发set-current只有匹配release_revision成功。

### WVR-06 权限与旧行为兼容

读历史沿 workflows.read+归属；复制/恢复/发布选择沿 workflows.manage+归属；执行仍 workflows.execute，Work权限/审批另外沿原规则。前端只读写控隐藏或禁用，后端不依赖前端。

不改已有固定版本 API Key/Agent/子流程调用，不把当前指针当凭据重定向。旧定义/版本继续支持，运行文字仍用已确认的原同步HTTP/查询方式，不加工作流SSE/异步202。

验收：两个账号不能读写互相版本；只有read的用户无写请求；恢复/复制不绕测试或审批；原15节点调试、模板、习惯学习和Ask SSE受影响范围回归。

### WVR-07 API 预期

在原 `/api/v1/workflows` 下增量实现，字段最终由开发文档对齐，不同接口不能混用版本意义：

- GET `/{id}`/列表：增 current_published_version、release_revision；保留原revision/definition/layout及旧调用。
- GET `/{id}/versions`：保留历史列表，包含可用状态、当前标识/布局是否存在的元信息，不回传模型密钥。
- GET `/{id}/versions/{n}`：完整只读快照；旧无布局明确标注，active=false也可读。
- POST `/{id}/versions/{n}/restore`：`{revision}`，新草稿revision、tested空；恢复前保护独立交接见补充。
- POST `/{id}/versions/{n}/copy`：`{name}`，返回独立新草稿id；不拷运行/凭据/权限。
- POST `/{id}/versions/{n}/set-current`：`{release_revision}`，返回更新后的 current 和 release_revision；无匹配409，不执行图。
- 原版本上下架继续，必要增加独立状态CAS；下线当前和清指针必须在同事务完成。普通上架不代表设当前。

本期不新增 current/runs，前端固定版本号后走既有执行接口。不删除单版、不支持跨用户导入或外部 DSL。

### WVR-08 平台软件发布追溯

工作流发布号不等于软件release。每次平台部署生成本地唯一 release_id（UTC时间+随机/源码摘要后缀），保存分支/HEAD（允许dirty）、**实际业务源码文件SHA清单和源码包SHA**、迁移版本、前端BUILD_ID、作者/独立审查/QA报告路径及测试批次数量/跳过/边界、部署时间和健康结果、当前状态备份标识。未提交工作区不能只写HEAD假称代码可复现。

复用现有部署脚本/备份机制，不新建监控服务，提交/push遵用户最新授权由根协调者执行，不以本功能隐式扩大仓库或远端范围。发布清单不含API密钥/环境秘密/用户数据，源码快照排除.env、数据目录和构建/依赖；数据备份仍按既有受保护机制单独保存。报告分辨“准备发布/已验证/部署成功/失败”，失败不写deployed。

验收：从当前release能定位源码摘要、对应构建和实际测试结果；源码包完整性可核、无凭据；重启后记录仍在；本轮测试/审查后再部署，当前用户状态/密钥摘要保留。软件追溯不以必须推送为前提；本轮推送仅按最新授权，不新增服务。

## 5. 交接与范围

开发据 WVR-01～08 写开发计划/迁移及排期；作者自验后独立审查，通过才交QA。QA按正常、并发409、来源缺失/停用、两个账号、dirty保护、运行固定版与旧布局逐条验证。测试不访问真实外部模型，使用隔离库和本机协议替身；本轮不能将此前全量结果冒充新回归。

产品本期不做全量草稿自动版本仓、多用户合并/分支、git远程操作、任意版本删除、跨团队分享、diff编辑器或DSL导入。恢复前的数据保护是必需闭环，具体最小备份方案在补充冻结后实施，不以不做自动版本仓为由丢失编辑。


## 恢复保护最终冻结补充（替代早期讨论中的两请求备份方案）

最终采用后端原子恢复：若本地 dirty，UI先按原CAS保存当前完整草稿，保存失败/JSON格式无效则不调用restore、不丢本地内容。用户确认后调用restore；后端在同一事务内锁定流程、核对revision、先将当前已存草稿完整复制为本人独立未测试/未发布的备份工作流，再把选中发布版恢复为原工作流新草稿。备份与恢复同时提交或同时回滚，失败/409不能残留假成功备份。

确认框明确“保存并备份当前草稿后恢复”及取消，不提供隐式丢弃，不写localStorage。成功返回恢复后的workflow及draft_backup_id/draft_backup_name，界面可从工作流列表访问备份。copy仍与原dirty草稿无关，不自动跳走；显式打开副本前保留/保存原编辑。

restore返回值需能区分新revision与独立备份，不将备份称为已发布历史。此设计真正保留已保存及刚刚保存的未保存修改，不把短暂PUT后覆盖宣传成保留。当前发布指针、历史发布版、原运行/Key保持不变。


## 旧结构兼容补充

历史原始 definition 不可变。能够由既有模型补齐默认值的旧节点，详情可同时提供 canvas_definition 规范化投影供渲染，完整历史配置仍展示原始快照。不要把旧节点缺 parameters 直接当损坏；无法支持的结构才只读原文并禁运行/恢复/复制。空布局统一按默认位置，不推断其创建年代。
