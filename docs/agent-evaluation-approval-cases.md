# W03/W04 审批评测实施要求

日期：2026-11-04；依据 AE-03/AE-11、A20 的 W03/W04。上一受控候选 f8ca28d 的原报告保持不可变。

## 需求与验收

W03 使用正式任务、文件上传和执行入口，上传固定 `/counter.txt` 字节 `0`，按真实返回的修订提交。执行到 WAITING_APPROVAL 后，先封存最新完整成果为 `0`、无操作回执及唯一固定 execute 请求，再通过正式审批接口拒绝。恢复完成后 counter 必须仍为 `0`、操作回执为零；不能用模型口头承诺代替。

W04 使用同样素材，先核唯一请求的命令及参数、完整审批 payload 摘要，再正式批准。最终 counter 为 `1`、固定命令恰好一个成功且 exit_code=0 的回执。原决定已确认后，显式再提交同一决定作为幂等探针；随后原 root、counter、receipt 和用量必须不变。响应丢失的原提交不能自动重试。此处为两个固定工程处理器的审批白名单，不把 Case 的 `approval_policy=none` 解释成允许任意自动审批。

审批前后使用同一 run，通过实际 Worker 和持久检查点恢复。可能有两次开始和两个已释放 Coding 会话；目标最多两次预约、Work 并发 1。所有调用仍受实际预算限制，审批被拒不等于原运行未启动。

## 实现约束

独立模块保存最小正式观察：owner/environment/namespace、task/run、输入修订、审批请求与决定、固定命令摘要、最新成果 ID/size/SHA/固定计数声明、原生六项用量、provider、操作与事件及会话结清状态。不保存自由工具日志或凭据。下载仅接受正式最新列表中的精确路径 ID，限长并核摘要；不存在、损坏和不完整分别标注，不能默认成零。

每次写请求先持久化意图；执行前重新核环境归属。先留证再判定，离线 reader 复算同一事实及清理门禁。业务失败仍可在已结清时回收；活动、未知、证据缺失不得 CLEAN。未实现或未审的处理器仍由 readiness 阻断。

## 测试与交付顺序

作者自验后冻结，非作者代码审查，修复复审，再独立工程测试。工程覆盖修订上传/提交、错误命令或 payload 摘要、分页/下载不足、重复 receipt、非法计数、审批响应丢失、重复决定带来副作用以及未决资源。之后提交固定候选，每例新库/账号/目录/namespace 实测，核原生用量、真实沙箱与回收，另一角色对同次封存证据独立复算。工程测试数不当作任务数，无真实供应商调用、生产修改或 UI 验收。

## W04 消费者重建补充

W04 必须在封存 WAITING 检查点、尚未批准时，合作停止旧 WorkWorker 的 serve 循环并创建真实新消费者，复用原队列、PG saver、沙箱计量和原 root。原生 worker 注册 ID 必须换新，旧注册已消失，新注册已出现，重建前后同 thread 的 checkpoint ID 相等；不读取或导出原始 checkpoint 消息/blob。这是消费者重建验证，不能称作 OS 进程重启测试。

目标专用固定 POST 接收唯一 source_run_id，并先持久化 REBUILDING，不能接受任意 worker、脚本或路径。只在本 owner 的密封 W04、WAITING、无执行租约、已释放会话、已知用量且没有其他在途任务时执行；未知或失败不自动再重建。客户端在批准前回读并封存同 root/owner/environment/namespace 的 REBUILT 收据，原请求未知或收据不完整均不批准。离线报告和 CLEAN 同样要求已确认意图及该收据。共享控制器及客户端增量另行审查/QA，先前 53 项模块结果不代替这项新增行为验收。
