# RDC 资源配置追溯体验观察与建议

日期：2026-11-03。状态：需求/源码观察及已有开发期HTTP记录整理；不是新UI体验验收，也不是独立QA结论。

## 观察依据与未验证范围

本文区分三种信息，不混用：

1. **产品目标**来自 `resource-reference-decoupling-requirements.md`。用户应能继续使用旧业务发布版本，普通配置维护不造成重发/新建任务负担；真正授权、兼容或审批目标变化才要求处理。
2. **源码信息架构**来自当前资源页、共享修改记录、通知投递及运行配置组件的静态阅读。只能说明代码计划呈现什么，不能证明部署环境已显示、窄屏可用或键盘操作正确。
3. **已执行HTTP观察**来自此前开发自验：真实应用路由和随机隔离PostgreSQL，外部模型/连接使用替身；最后一次相关组合为24项通过。其身份是作者自测，不是独立验收，不代表整个RDC范围通过，也没有证明真实供应商或真实收件效果。

实际3100/3131页面访问此前被工具拒绝。此后没有访问或绕过，也没有实际浏览新“修改记录”“本次资源配置”及通知目标确认界面。Playwright仅发现了5个新增测试用例，未执行页面步骤。构建/类型检查通过也不能当作页面体验证据。后续实际页面验收须单列授权、环境和证据。

## 1. 从原问题出发的用户旅程

用户原本在使用“自动任务助手”发布v1时遇到模型修订不一致错误。对用户而言，模型地址或密钥维护属于平台配置工作，既有任务逻辑并未改变。理想路径是继续选择原助手v1创建任务；运行详情清楚显示“业务版本v1，实际模型配置修订3”，异常时能沿该记录查看相关修改。

应减少让用户理解内部修订机制的负担。保存普通配置无需新增确认弹窗，也不应让用户猜要重新发布哪一层。需要确认的是新的接收方、变更后的脚本/操作目标、无法安全延续的恢复阶段，而不是每个递增数字。

这条端到端旅程尚未完成实际页面验证。后续验收必须真实操作一次“维护模型→用原助手创建任务→查看实际配置→回看维护历史”，不能仅分别证明四个组件可以渲染。

## 2. 源码中的入口组织

当前实现沿用原有管理位置，未新增独立管理中心：

- 管理员在模型设置、MCP卡片和模型路由展开修改记录。
- 私有知识库在配置页、长期记忆在检索设置附近、仓库与通知通道在各自卡片展开修改记录。
- 运行详情提供“本次资源配置”，承载本次配置、当前差异、调用/阶段及恢复相关信息。
- 通知投递记录显示原目标、当前目标、暂停原因和重发来源。

这与需求要求的“在资源与运行原位置排查”一致。共享修改记录采用按需加载；展开历史不应改变正在编辑的设置。实际页面仍需检验历史入口是否足够明显、卡片展开后是否过长，以及返回运行时是否保留原选择状态。

只读通知入口曾因只挂载给manage角色而不可见，现源码已改为read角色可查看，写入口由canManage控制；后端GET也改为notifications.read。此前真实HTTP自验只验证了接口权限，不能据此声称按钮可见性、焦点顺序和列表布局已经验收。

## 3. 已执行API观察能证明什么

此前开发自验通过真实HTTP和事务验证了以下行为：

- 服务器记录真实登录操作者，伪造X-Actor/X-Change-ID不能改变记录来源。
- 切换默认模型时新旧默认的历史可以用同一关联ID对照，不同请求的ID区分。
- CAS失败没有额外成功历史；删除后原owner仍能看记录，其他owner即使是管理员也不能因此读取私有历史。
- 只有通知read权限可以读取本人安全通道信息及修改记录，不能停用通道或重新投递。
- 用户看到目标B后后台改成C，用B摘要确认会被拒绝且不新增投递；刷新确认C后才建立新投递，并保留retry_of关联。

这些现象支持“历史可信、失败不伪装成功、确认内容不能被悄悄替换”的产品方向。HTTP返回码和字段存在并不能证明用户能理解它们；目标摘要、操作者UUID、原/当前差异仍需要实际页面检查。

没有执行真实外部通知、真实仓库push/PR或供应商模型效果验证。此前通知协议回归只用了本机受控接收器；“渠道已接收”仍不等于收件人已阅读。

## 4. 优先体验建议

### 4.1 先说用户应该做什么，再呈现修订和摘要

错误标题应直接说明“模型已停用”“向量兼容性待核对”“审批目标已改变”“恢复配置待确认”。下一句说明受影响的节点/成员/资源及可用处理入口。修订、UUID和摘要放次级信息中，供排查定位。

普通更新不增加阻断提示。用户没有发起排查时，无需每次调用展示“已采用最新修订”。异常运行可以直接展示业务版本与实际资源，不让用户在模型管理页猜发生过什么。

### 4.2 明确区分当时配置、当前配置与未记录

“修改前/修改后”适用于同一次成功配置修改；“本次使用/当前配置”适用于运行对比。两组文案不要互换。

基线必须写明“上线时建立，无法还原此前修改”；解析后未调用要标为“已解析，未调用”；旧运行缺快照要明确“历史未记录”。不能让当前配置填满空白后给人以完整历史的错觉。

公开快照的“凭据修订标识”只用于定位轮换，不是可恢复的旧密钥。建议界面沿用这一表述，避免“凭据摘要”让用户误以为点击即可查看或复用密钥。

### 4.3 操作者与关联操作更易读

当前历史组件可以显示actor_name，缺失时回退用户UUID。建议在保持服务端可信来源与权限边界的前提下提供当时可安全显示的操作者名称；UUID保留为辅助定位。系统来源展示具体任务名，避免只有笼统system字样。

默认切换的关联ID有用，但长ID本身不等于用户理解联动。可以补充“同次操作还改变了默认模型标记”的简短说明，或在权限允许时定位另一侧记录。不得为方便联动跳转扩大跨owner权限。

### 4.4 通知确认要围绕接收目标

原目标与当前目标应并列易辨，确认文案重复显示将采用的当前host及目标标识，取消不产生写请求。相同host但摘要不同，应说明“同一服务地址下的接收目标已变化”，不能让用户只比较host就认为相同。

host和摘要属于安全展示的定位线索，不能独立证明收件人身份。若未来提供易读接收方标签，应由受控配置产生并明确其含义，不能通过展示完整Webhook路径/query来提高可读性而泄露机器人凭据。

UNKNOWN需先核对收件情况；用户明确确认重复风险后才重发。重发记录和原记录都保留，当前状态不要覆盖未知结果的原始证据。历史缺失时说明不能安全自动重发，而不是给一个点击后才失败的按钮。

### 4.5 降级不能伪装正常

索引身份、维度或预处理不匹配，应说明本次是否退回关键词、可能漏掉什么，以及去哪里核对/重建。不能仅给“没有结果”，也不能把所有旧向量跳过后仍显示无告警hybrid。

独立审查已经针对维度告警、同运行检索设置固定、模型主体与能力原子读取提出具体问题；本体验建议不判断修复已完成。只有修复复审后再做实际交互和API验收，才能把原因说明与真实行为对齐。

### 4.6 中文时间、窄屏和编辑状态需要实测

源码使用中文本地时间格式；建议明确显示时区，避免不同浏览器时区造成排查歧义。长UUID、摘要、字段值需换行，手机上前后值可以纵排。

实际验收应检查390/320像素、键盘展开/关闭、加载和权限失败、切换资源、刷新历史，以及打开历史时未保存表单是否保留。当前没有页面截图或实际焦点记录，不能声称这些体验已经良好。

## 5. 后续实际体验清单

在修复与独立复审完成、页面访问获得允许之后，再从普通使用者角度执行：

1. 原助手版本在模型维护后创建并完成一次任务，不进行额外发布。
2. 从一次受控失败运行找到本次配置、相关修改及当前差异，再返回原运行。
3. 使用只读角色查看本人记录，确认没有写入入口；换其他账号确认无私有信息泄漏。
4. 处理一次目标变化的待通知消息，比较原/当前目标，取消一次，再刷新目标后明确确认；核对两条投递记录。
5. 处理一次未知向量兼容和一次待确认恢复，确认提示具体、操作范围清楚且未重复外部副作用。
6. 按窄屏和键盘路径重复关键步骤，保存获准环境中的截图、事件和问题记录。

在这些步骤实际执行前，应向用户明确报告“后端替身自测已有证据，实际新页面与真实外部服务尚未验收”，不以“已体验完成”代替缺失证据。
