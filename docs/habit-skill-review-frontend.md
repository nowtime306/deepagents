## 第一轮发现 HSK-FE01 / P2：未生成候选可暂停，却无法通过恢复操作重新采集

界面向所有非 forgotten 候选提供“暂停/恢复”，包含仅 1～2 条证据且 skill_id=null 的 learning 候选。暂停写入 disabled 后，恢复发送 enabled=true；后端 toggle 对非手工确认且证据不足3条返回 HABIT_EVIDENCE_INSUFFICIENT。自动观察又不能向 disabled 状态积累，因此界面引导的对应恢复路径不成立。当前组件用例先纠正生成子 Skill 再暂停，未覆盖此情形。

建议：遵循“停用生成资产”的最小范围，只对已有生成 Skill 提供暂停/恢复，候选保留采纳/遗忘；或者将不足门槛的候选恢复为 learning 而不是 active，仍不得绕过三消息生成。需作者选择并增加对应反例自验，然后独立复审。

本项由静态 UI→API 调用链确认，未称为已经由真实浏览器重现。当前结论为待修复，不以现有13通过覆盖该新反例。

## 已检查的行为

- 启用顺序：具备绑定权限时先 install 再 PUT enabled；资源合并由后端 install 执行，UI没有覆盖整份知识库/MCP/Skill绑定数据。缺绑定权限不擅自安装，已授权独立 Agent 仍按原资源流程使用。
- resourcesRevision 的读取 controller 与动作 request controller 分开，外部资源刷新不直接取消写操作；load 通过 readVersion 防止迟到设置结果覆盖新数据，动作失败/409后清理忙态并重新读取当前记录。
- 修正/暂停/遗忘/重新学习均携当前修订；409关闭旧编辑器后加载最新数据，后续提交需重新打开。遗忘和关闭学习的不同效果有明确文案，未承诺删除原会话或用户手工 Skill。
- 来源只从后端返回的本人证据取会话 ID，无自行构造外部 URL 或来源正文复制；chat.read 控制入口，打开来源复用原会话导航及后端授权。只读界面无写按钮/可写开关。
- 新权限入口以 knowledge.read/skills.read/tools.read/memory.read 任一可见能力中心，初始页签选本人获准项且隐藏未获准页签；skills.read 只读用户不再被迫获得知识库权限，也不从默认知识页发出无权请求。
- CSS只作用于习惯区域，窄屏操作可换行；实际390px以作者/QA浏览器为准。PlatformApp改动仅最小权限导航判断与来源回调，未修改 Ask SSE 订阅。

## HSK-FE02 / P2：新增只读 Skill 入口仍暴露旧资源卡写操作

将能力中心入口正确开放给 skills.read 后，旧 Skills 页的导入文件、停用/启用、删除和绑定控件尚未与当前权限一致。只读用户虽然不能从后端成功越权，仍会看到并能触发会返回403的写请求；本轮只校验 HabitLearning 区域的无写控不足以证明整个新入口只读。

最小修复范围：Skills 分支按 skills.manage 隐藏或禁用上传、停启和删除；绑定复用现有 chat.read/chat.manage 的 canBind 禁用条件，查看技能资源保持可用。不重构其他管理页，也不取消后端权限检查。当前 bind() 实现没有额外 canBind 提前返回，不以不存在的前端守卫解释安全性。

应补充只读用户整个 Skills 页的控件/零写请求断言，且不为展示 Skill 授予 knowledge.read 或发无权知识库请求。作者定向修复及自验后需增量复审。该项是新入口联动的可操作性问题，不记录为已发生后端越权。
