# 知行平台开发版本控制

2026-11-03起按用户授权：在onwer_agent提交并推送origin，分支和每次提交独立留档。平台软件版本与用户工作流v1/v2是两套编号，不修改Deep Agents上游SDK包版本。

## 固定流程

1. 需求、Demo与测试用例先明确；每个功能保留开始时的Git提交作为基线。
2. 开发者自验 → 独立代码审查 → 修复复审 → 独立测试。未通过的功能不得写成已验收或部署成功。
3. 按功能提交，记录确切提交号、分支、远端和对应需求/报告；忽略本地数据、密钥、真实环境文件与依赖构建产物。
4. 已验收软件用zhixing-vMAJOR.MINOR.PATCH标签，例如初始基线zhixing-v0.1.0。新增兼容功能升MINOR，修复升PATCH，不复用或改写旧标签。
5. 创建只含Git提交源码的发布包与文件SHA256清单，再备份当前数据、迁移/部署、独立健康检查，记录BUILD_ID和发布状态。源码包不等于数据库回滚，数据库不得自动恢复旧备份。
6. 正常推送分支与标签；禁止强推或覆盖远端历史。无法推送时保留本地提交并明确错误，不伪称远端已同步。

## 记录位置

- [版本与分支记录](releases/history.md)：可随源码查看的持久日志。
- `.local/releases/<版本>/release.json`：提交、标签、源码包/业务文件SHA、报告、部署时间/BUILD_ID/状态；不含用户数据或密钥。
- `.local/releases/<版本>/source.zip`：确切Git提交源码，不以dirty工作区冒充该提交。
- 原数据备份沿用services/api/.local/backups；与可分享源码包分开存储。

## Windows 验收摘要

工作区可能同时存在旧CRLF检出文件和新增LF文件。`prepare`仅对自己的归档命令设置`core.autocrlf=false`，不改用户Git设置或重写工作区；发布清单的`source_sha256`记录归档字节摘要。

最终QA JSON的`source_sha256`须与归档完整清单一致，另用`worktree_sha256`记录真正被测试和构建的每个业务文件原始字节摘要，测试前后需保持不变。两者不能互相冒充：工具先严格匹配QA原始摘要，再核对归档；只允许严格UTF-8且无NUL文本的CRLF到LF差异，正文、空白、BOM、二进制差异仍拒绝。未提供原始清单的旧QA只适用于字节与归档完全相同的工作区。

这不会放宽真实页面验收、固定提交标签、完整部署/健康、文件集合或私密文件排除门槛。独立审查和反例见[Windows发布审查](windows-release-review.md)。
