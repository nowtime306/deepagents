- 生产 Ask 改为独立后台消费已提交 task_runs。API 只持久入队和提供事件，重启不清除 Worker 的运行或排队记录。测试可使用原有进程内执行以验证旧接口兼容；生产环境默认独立 Worker。
- 采用与 Work 一致的 60 秒租约、心跳、取消和过期审阅原则。过期执行明确失败为结果未知，不自动再次请求模型或重放工具。后续新一轮提问显式发起；检查点中未完成工具调用用“结果未知”占位关闭，不把占位当成功结果。
- 每次执行的 PostgreSQL 检查点连接同时持有会话 advisory lock。连接断开时该执行的检查点写入也失效，不自动换连接继续写。其他 Worker 必须获得该会话锁，避免同一会话的新旧执行交错。
- 事件和消息写入校验运行租约；终态不允许失效 Worker 覆盖。实际迟到的服务商用量仍可补记至原调用，不伪造为零或重复计费。
- 独立 Worker 复用现有资源授权服务；向量索引由 API 独占，通过持有短期运行租约的内部接口检索，不复制宿主凭证至浏览器。API 不可用时检索明确失败，而非假称已有检索结果。
- 运行诊断补排队/租约状态、上下文组成、压缩和重复工具调用的受控信息；不把参数、密钥或推理正文写入公共日志。

验证要求：隔离数据库中的多 Worker 认领竞争、租约过期、取消、API 重启、失效事件/消息拒绝、检查点锁排他及断连、新一轮关闭未完成工具消息、原会话与账本兼容；实际本机协议替身证明 API 重启期间 Worker 继续。真实模型请求继续跳过。

参考：[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[PostgreSQL advisory locks](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS)。采用本地已安装依赖源码核对接口，不引入第二层模型循环。
